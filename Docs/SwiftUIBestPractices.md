# 📐 Best Practices SwiftUI: вёрстка для iPhone и iPad

> Материал предоставлен пользователем 28.10.2026 и адаптирован к решениям проекта. Служебные подписи и favicon-ссылки из вставленного текста удалены.

**Решение проекта от 28.10.2026:** Dynamic Type не поддерживаем. Размеры текста, кнопок и иллюстраций задаёт дизайн-система; они не масштабируются вслед за системной настройкой размера текста. Адаптация к размеру окна iPhone/iPad и локализации остаётся обязательной.

Ниже — набор правил, который я бы рекомендовал принять в вашей команде при переходе с UIKit на SwiftUI. Их можно использовать как стандарт разработки и чек-лист для Code Review.

Основной принцип:

Мы не верстаем экран под конкретный iPhone или iPad. Мы создаём интерфейс, который адаптируется к доступному пространству, содержимому и локализации.

Интерфейс должен корректно работать при изменении размера окна, ориентации и локализации.

## 1. Базовые правила вёрстки

| Правило                                                                   | Приоритет     |
| ------------------------------------------------------------------------- | ------------- |
| Использовать нативные контейнеры `VStack`, `HStack`, `Grid`, `ScrollView` | Обязательно   |
| Не рассчитывать вручную размеры всего экрана                              | Обязательно   |
| Предпочитать гибкие размеры фиксированным                                 | Обязательно   |
| Учитывать Safe Area                                                       | Обязательно   |
| Использовать размеры типографики из дизайн-системы                        | Обязательно   |
| Поддерживать изменение размера окна iPad                                  | Обязательно   |
| Использовать дизайн-токены для отступов и размеров                        | Рекомендуется |
| Ограничивать максимальную ширину контента                                 | По ситуации   |
| Использовать `GeometryReader` только при необходимости                    | Рекомендуется |
| Проверять разные ориентации и локализации                                 | Обязательно   |

## 2. Не задавать фиксированные размеры без необходимости

В UIKit мы привыкли явно описывать геометрию элементов. В SwiftUI обычно лучше позволить системе рассчитать размеры.

Нежелательно

```
VStack {
    Text("Добро пожаловать")
    Text("Управляйте своим домом")
}
.frame(width: 350, height: 240)
```

Предпочтительно

```
VStack(spacing: 16) {
    Text("Добро пожаловать")
    Text("Управляйте своим домом")
}
.padding(24)
.frame(maxWidth: 480)
```

Во втором варианте:

- Высота определяется содержимым.
- Ширина не превышает 480 pt.
- На узком экране блок может сжаться.
- При длинном переводе или большем объёме текста блок может стать выше.

Исключения: размеры иконок, аватаров, индикаторов страниц, кнопок по дизайн-системе и других элементов, которым действительно нужна определённая геометрия.

## 3. Не определять интерфейс через `UIDevice.current.userInterfaceIdiom`

Нежелательно

```
let isPad = UIDevice.current.userInterfaceIdiom == .pad

VStack {
    content
}
.padding(isPad ? 60 : 20)
```

Предпочтительно

```
@Environment(\.horizontalSizeClass)
private var sizeClass

var body: some View {
    content
        .padding(sizeClass == .regular ? 32 : 16)
}
```

`horizontalSizeClass` описывает характер доступной ширины:

- `.compact` — компактная ширина.
- `.regular` — обычная или расширенная ширина.

Но есть нюанс: `regular` — не конкретное число точек. Два окна одинакового класса могут иметь существенно разную ширину.

Поэтому Size Classes подходят для выбора общей структуры интерфейса, но не заменяют проверку реального доступного пространства. На iPad в маленьком окне интерфейс должен оставаться удобным, а не пытаться показывать полноэкранную планшетную композицию.

Исключение для `userInterfaceIdiom` допустимо, если требуется именно платформенное поведение, а не адаптация размеров.

## 4. Использовать адаптивные контейнеры SwiftUI

Вместо ручного определения размеров используй готовые инструменты SwiftUI.

| Инструмент               | Когда использовать                                                              |
| ------------------------ | ------------------------------------------------------------------------------- |
| `VStack` / `HStack`      | Обычное вертикальное и горизонтальное расположение                              |
| `Spacer`                 | Распределение свободного пространства                                           |
| `Grid`                   | Небольшие таблицы и сетки                                                       |
| `LazyVGrid`              | Большие адаптивные сетки                                                        |
| `ViewThatFits`           | Когда нужно выбрать компоновку, которая помещается                              |
| `AnyLayout`              | Когда нужно динамически менять тип компоновки, сохраняя состояние дочерних View |
| `GeometryReader`         | Когда действительно нужно знать размер контейнера                               |
| `containerRelativeFrame` | Когда размер элемента зависит от ближайшего поддерживаемого контейнера          |

Apple рекомендует в первую очередь использовать встроенные контейнеры и переходить к кастомной геометрии только тогда, когда стандартные решения недостаточны.

Например, `ViewThatFits` (iOS 16+) позволяет выбирать подходящее расположение без проверки типа устройства.

```
ViewThatFits(in: .horizontal) {
    HStack(spacing: 16) {
        Image("Welcome")
        Text("Добро пожаловать")
    }
    .fixedSize(horizontal: true, vertical: false)

    VStack(spacing: 16) {
        Image("Welcome")
        Text("Добро пожаловать")
    }
}
```

Сначала SwiftUI попробует горизонтальную компоновку. Если она не помещается по ширине, выберет вертикальную.

Это удобно для адаптации между узкими и широкими окнами. Если нужно сохранить состояние дочерних View при изменении компоновки, рассматривай `AnyLayout`.

## 5. На iPad адаптировать композицию, а не растягивать iPhone

iPhone

Одна колонка

iPad

Две колонки

Для контента, который не должен занимать всю ширину планшета, можно использовать:

```
VStack(spacing: 24) {
    content
}
.frame(maxWidth: 640)
.frame(maxWidth: .infinity)
.padding(.horizontal, 20)
```

Первый `frame` ограничивает ширину, второй центрирует композицию в доступном пространстве.

А если нужны адаптивные карточки:

```
let columns = [
    GridItem(.adaptive(minimum: 220), spacing: 16)
]

ScrollView {
    LazyVGrid(columns: columns, spacing: 16) {
        ForEach(devices) { device in
            DeviceCard(device: device)
        }
    }
    .padding(20)
}
```

SwiftUI самостоятельно разместит столько колонок, сколько влезет при минимальной ширине карточки 220 pt.

Для небольшого фиксированного числа элементов можно использовать обычный `Grid`, не обязательно `LazyVGrid`.

## 6. Использовать Safe Area, а не рассчитывать её вручную

Вместо расчётов высоты экрана и отступов до Home Indicator лучше применять `safeAreaInset`.

Пример экрана с закреплённой снизу кнопкой:

```
ScrollView {
    content
        .frame(maxWidth: 720)
        .frame(maxWidth: .infinity)
        .padding(20)
}
.safeAreaInset(edge: .bottom, spacing: 0) {
    Button("Продолжить") {
        nextPage()
    }
    .buttonStyle(.borderedProminent)
    .frame(maxWidth: 480)
    .padding(.horizontal, 20)
    .padding(.vertical, 12)
    .frame(maxWidth: .infinity)
    .background(.regularMaterial)
}
```

SwiftUI учитывает пространство, занятое кнопкой, поэтому прокручиваемый контент не должен оказываться под ней.

`ignoresSafeArea()` применяй преимущественно к декоративным фонам и изображениям, которые действительно должны выходить за границы Safe Area.

## 7. Не запрещать интерфейсу увеличиваться по высоте

Это необходимо для длинных переводов, многострочного текста и изменения ширины окна.

Плохо

```
Text("Описание устройства")
    .font(.system(size: 16))
    .frame(height: 20)
    .lineLimit(1)
```

Лучше

```
Text("Описание устройства")
    .font(.system(size: 16))
    .fixedSize(horizontal: false, vertical: true)
```

Размер шрифта задан дизайном, а текст может занимать несколько строк. `fixedSize` используется точечно, когда нужно дать тексту его естественную высоту. Для своих шрифтов используем `Font.custom(..., fixedSize: ...)`; масштабирование через `relativeTo` и `@ScaledMetric` для системного размера текста не добавляем.

## 8. Использовать `GeometryReader` только для реальных измерений

`GeometryReader` — не аналог `UIScreen.main.bounds` и не обязательный корневой элемент каждого экрана.

Он подходит для:

- Пропорциональных размеров сложной композиции.
- Зависимости интерфейса от размеров конкретного контейнера.
- Кастомных графиков, каруселей и других геометрически зависимых компонентов.

Например:

```
GeometryReader { geometry in
    Image("Banner")
        .resizable()
        .scaledToFill()
        .frame(
            width: geometry.size.width,
            height: geometry.size.width * 0.6
        )
        .clipped()
}
.aspectRatio(5 / 3, contentMode: .fit)
```

Здесь вычисления оправданы: высота изображения зависит от ширины.

Но для обычного баннера проще:

```
Image("Banner")
    .resizable()
    .scaledToFill()
    .aspectRatio(5 / 3, contentMode: .fit)
    .clipped()
```

Правило: если задача решается через `padding`, `frame`, `aspectRatio`, `Spacer` или стандартный контейнер, обычно не нужен `GeometryReader`.

## 10. Не использовать магические значения для компенсации проблем вёрстки

Например, в твоём онбординге:

```
static let headerHeight: CGFloat = 180
static let pageBottomReserve: CGFloat = 220
static let minimumFooterHeight: CGFloat = ...
```

Сами по себе константы нормальны. Но стоит различать:

- Дизайн-токены: отступ 16, радиус 12, высота кнопки 56.
- Компенсирующие вычисления: вычесть 220 из высоты экрана, чтобы футер оказался в нужном месте.

Первое — хороший подход. Второе — признак, что стоит поискать более естественную композицию.

При этом фиксированная высота `TabView` со стилем `.page` может быть оправдана, особенно внутри `ScrollView`.

## 11. Правила для команды при переходе с UIKit

Я бы дополнительно закрепил следующее:

- Компонентность. Повторяющиеся элементы — в самостоятельные `View`, стили — в `ButtonStyle` и `ViewModifier`, а согласованные размеры — в дизайн-токены.
- Никаких UIKit-обёрток без причины. Не создавать `UIViewRepresentable`, если есть полноценное SwiftUI-решение. Но и не запрещать UIKit там, где нужен функционал, которого нет в SwiftUI.
- Стабильная идентичность. Для `ForEach` использовать реальные стабильные ID, а не генерировать `UUID()` при каждом построении `body`.
- Разделение ответственности. `View` отвечает за отображение и пользовательские действия; сетевые запросы, бизнес-правила и преобразование данных не должны жить внутри вёрстки.
- Accessibility. Учитывать VoiceOver, Reduce Motion, достаточно крупные области нажатия и правильный порядок чтения.

### Главное правило, которое я бы закрепил в проекте

Каждый новый SwiftUI-экран должен по умолчанию поддерживать iPhone, iPad, изменение размеров окна и локализацию без ручного расчёта геометрии устройства. Типографика использует фиксированные размеры дизайн-системы.

Отступы, размеры и ограничения должны описывать дизайн, а не компенсировать поведение конкретного устройства.

Документация Apple, на которую стоит ориентироваться: [Human Interface Guidelines — Layout](https://developer.apple.com/design/human-interface-guidelines/layout?utm_source=chatgpt.com) и [SwiftUI Layout Fundamentals](https://developer.apple.com/documentation/swiftui/layout-fundamentals?utm_source=chatgpt.com).
